Heading 3: 5.3.2 Database Implementation
Normal: The relational schema represented users, agent profiles and verification attempts as separate entities. UUID primary keys identified records, and foreign keys linked each agent to a user and each request to an agent and document. Unique constraints on user email, the agent-to-user reference and the national identity number limited duplicate accounts and profiles. Verification scores and decisions used unique request references so that each request had at most one score row and one decision row. Table 5.4 summarises the core entities. The implemented schema uses snake_case attribute names. Foreign keys and unique constraints define relationships, but successful processing is needed to create the corresponding score and decision records.

Entity | Important contents | Purpose

documents | document_id, agent_id, file_url | Evidence references for an agent

Normal: Request status values distinguished pending, verified, review and rejected requests. The decision enumeration excluded pending because it represents completed classifications. The decision_basis field distinguished SVM classifications from placeholder threshold decisions, which allowed stored outputs to be interpreted correctly when model inference was unavailable. Row-level security was enabled in the base schema with policies supplied in separate scripts, and the backend independently validated bearer tokens through Supabase and checked roles before protected actions.
Normal: The inspected documentRetentionService.js considers the latest request for each agent and skips it unless its status is verified. For eligible verified cases, the audit window expires three business days after the successful decision; business days are Monday to Friday in Africa/Nairobi, without public-holiday exclusions. The job runs at startup and every fifteen minutes while the backend is running. It removes eligible image objects and clears file references while retaining document rows, scores, decisions and audit history. Failed removals leave references available for a later cleanup attempt. This describes the source; live deletion scheduling and object removal have not been demonstrated.
Normal: The amended DR-08 instead requires each pending, review or rejected image to expire 30 calendar days after upload, including abandoned uploads. Viewing or a status change must not restart this deadline. Verification metadata, scores, decisions, consent records and related audit history are to expire 180 calendar days after attempt closure, unless a documented lawful preservation obligation applies. Closure is a final verified or rejected decision, or expiry of an incomplete attempt. These are proposed project periods, not statutory retention periods.
Normal: The current verified-only purge does not implement the 30-day policy, an abandoned-upload expiry path, the 180-day metadata lifecycle or the preservation-exception record. The amended DR-07 limits metadata preservation to its defined period, and NFR-06 requires signed URLs not to outlive the applicable image deadline. The existing verified-case window supplies only part of this behaviour. Expiry enforcement for non-verified evidence and safe reapplication after restoration remain implementation and testing gaps.
Heading 3: 5.3.3 Application Modules
Normal: Authentication, roles and passkeys. Authentication middleware rejected missing or invalid bearer tokens, and role middleware restricted administrator operations. Email/password and Google sign-in were supplemented by WebAuthn passkeys using SimpleWebAuthn. The public.passkeys table stored the credential identifier, public key, signature counter, transports, device type, backup status, label and device metadata; the application did not receive device fingerprint or face templates from WebAuthn. Challenge and rate-limit records were stored separately. Client support detection controlled which passkey actions were offered. WebAuthn relying-party, origin and fresh-challenge validation are distinct from the HTTP CORS policy (World Wide Web Consortium, 2021).
Normal: Human check. The internal captcha.js utility generates a five-character image challenge, stores its answer in process memory and sets a five-minute lifetime. The first validation attempt consumes the challenge, whether the answer is correct or incorrect. authController.js checks the CAPTCHA before calling password authentication and returns missing/invalid-challenge feedback. LoginPage.vue provides a refresh button and a labelled input. No external CAPTCHA provider is integrated.
Normal: A process restart loses outstanding challenges, and separate backend processes do not share the in-memory challenge map. A challenge generated on one instance may therefore fail on another unless deployment routing or a shared store addresses this. Neither arrangement was verified. The image description and refresh control do not provide a non-visual solution. Google sign-in and optional registered passkeys are other account-access paths, but their availability and accessibility do not establish an equivalent alternative for every password user. The accessible-alternative part of IR-11 and restart/multiple-instance behaviour remain untested.
Normal: Browser integration. The HTTP, Socket.IO and AI CORS settings described in Section 5.2.2 are source findings. An allowed origin does not bypass authentication, and absence of an Origin header is not proof of a trusted caller. Production origin separation, permitted/unlisted-origin preflights and real-time behaviour require C4-T26 execution against the actual deployed configuration.
Normal: Registration and evidence capture. Agents entered personal details and supplied document and selfie images through the capture interface. Server upload middleware accepted JPEG and PNG MIME types and imposed a 5 MiB limit per file, returning a validation message for unsupported or oversized files. Registration logic checked existing national identity numbers. The storage integration used a private Supabase bucket; its deployed access settings were not live-tested in this update.
Normal: Disclosure and consent. The inspected frontend, backend and database files did not contain the proposed pre-collection consent control, a corresponding account/purpose/notice-version/server-timestamp record, backend enforcement of that record, or withdrawal handling. Under amended DR-09, these controls are required where consent is the approved processing basis. Account registration and submission of images do not demonstrate that this requirement has been met. Both the collection controls and the applicable processing basis remain unresolved; the proposed notice alone does not close DR-09.
Normal: Verification pipeline. Four services produced the evidence signals. The quality service computed sharpness as Laplacian variance, brightness as the mean HSV value channel and contrast as the grayscale standard deviation, and images below the configured thresholds were rejected with specific messages before further processing. The OCR service compared the extracted name, identity number and date of birth with the registered details. Face matching compared document-portrait and selfie embeddings generated with the ArcFace implementation in InsightFace (Deng et al., 2019), and liveness scoring used the Silent-Face anti-spoofing models. These were evidence signals: neither text agreement nor facial similarity alone proved that a document was authentic.
Normal: The backend sent the evidence to the quality, OCR, face and liveness endpoints and assembled six numerical features, defined in Table 5.5. Raw image-quality measurements were kept in their original units, and MinMax scaling was applied inside the model processing path. Missing, non-finite, wrongly typed or out-of-range evidence was rejected rather than converted to zero.

Heading 3: 5.3.5 Exception Handling and Decision Provenance
Normal: At the AI endpoint, an unavailable or inconsistent model bundle produces an unavailable-service response. At application level, complete valid scores may enter threshold fallback when SVM inference is unavailable or unusable. The decision basis is placeholder_threshold, and the rule outputs are not calibrated probabilities. These application paths are outside the model-only results in Section 5.4.3.
Normal: In verificationService.js, SVM_TIMEOUT_MS defaults to 5000 milliseconds and can be overridden by the environment. A separate AbortSignal timeout applies to the status request and then to the prediction request. This is not a five-second deadline for the complete verification workflow. The deployed timeout value, an overall verification deadline and a uniform bounded retry policy were not verified. No longer timeout, warm-up schedule or minimum-replica arrangement is claimed as configured.
Normal: The source distinguishes a status-request transport failure, a reported unavailable model, a prediction transport failure, a prediction HTTP error and an invalid prediction. A non-successful status response can be reduced to modelLoaded: false, so the resulting model-unavailable reason does not by itself distinguish every upstream status error. Diagnosis requires the status/prediction response details and service logs, with cold and warm measurements recorded separately.
Normal: accessControlService.js attempts to append KYC_DECISION_MADE with details.svmFallback = true, details.reason, the request and agent context and a system actor. auditLogger.js may return null if insertion fails. A logging attempt therefore does not prove that the reason persisted. The four historical placeholder decisions require matching audit rows and backend/AI logs joined by request identifier and time. Those matching records were not available; their failure causes and hosting environments remain unknown. I do not attribute them to Azure cold starts.
Heading 3: 5.3.6 Dataset Description and Preparation
Normal: The decision-model dataset contained 10,000 synthetic cases: 6,000 Verified, 2,000 Manual Review and 2,000 Rejected. Each record held the six features in Table 5.5 and a class label. The class quotas were experimental assumptions and not estimates of operational prevalence. No genuine identity records were used because real agent data raises privacy and consent concerns.
Normal: The generator reused stored benchmark measurements: 1,000 LFW face pairs, 1,200 NUAA presentations and 500 MIDV quality frames together with MIDV OCR measurements. The machine learning README and dataset metadata recorded summary statistics and file hashes. These historical measurements informed score distributions; the source images were not reprocessed during the version 3 experiment or this documentation update. None of the benchmark sources supplied the three-class KYC labels.
Normal: Face and liveness values were sampled from truncated distributions informed by the recorded measurements. OCR and image-quality values combined measured statistics with explicit simulation assumptions, and quality used a multivariate distribution over transformed blur, brightness and contrast. Some unresolved and genuine scenarios deliberately shared observed distributions to represent information that is absent from the six features. The labels therefore reflected assumed latent scenarios and not a threshold applied to the observed scores.
Normal: Exact and near-duplicate checks were run before partitioning. Row identifiers and latent scenario descriptions were excluded from the predictors, and scaling and optional quality transformations were fitted within training folds to avoid leakage. These checks screened close observations but could not show that the simulated population represents real applicants. The licence and redistribution terms of the benchmark datasets were not assessed here, and no redistribution claim is made.

Heading 3: 5.3.7 Model Training, Selection and Packaging
Normal: An RBF support vector machine combined the six features into a three-class decision (Pedregosa et al., 2011). Training compared C values of 0.1, 1, 10 and 100 with gamma values of 0.001, 0.01, 0.1, 1, scale and auto, giving 24 combinations per grid. Five-fold shuffled stratified cross-validation used macro F1 as the score, balanced class weights and seed 42, and preprocessing stayed inside the cross-validation pipeline.
Normal: For each parameter combination, the 7,000 training cases were divided into five stratified folds of approximately 1,400 cases. A fresh SVM was fitted on four folds (approximately 5,600 cases) and assessed on the remaining fold; the held-out fold changed across five rounds. Macro F1 was averaged across the five validation results. The 24 combinations therefore required 120 fold-level fits per grid, followed by refitting the selected configuration on all 7,000 training cases. Scaling was fitted only on the training portion of each fold. The calibration, selection and fresh evaluation cases were excluded from this cross-validation process.
Normal: The version 3 experiment compared raw and transformed quality inputs, native multiclass and explicit one-versus-rest SVM variants, and sigmoid, isotonic and temperature calibration. Three additional grids were fitted, and the earlier raw-native winner was reused with its provenance recorded. Calibration used only the calibration partition. Candidate selection used the separate selection partition and applied safeguards on macro F1, review recall and both false-verification counts relative to the comparable calibration baseline.
Normal: The selected configuration was raw_native_sigmoid with C = 10 and gamma = scale, and its training cross-validation macro F1 was 0.672766. Its probability policy used a review multiplier of 1.0, a verification threshold of 0.0 and a verification margin of 0.0, so no extra conservative verification threshold was applied beyond the selected policy.
Normal: The release gate required strictly higher accuracy on the fresh set, non-decreasing macro F1, and no increase in either Rejected-to-Verified or Manual-Review-to-Verified errors relative to the saved version 2 incumbent on the same fresh records. The selected candidate passed the gate and was promoted to the local version 3.0.0 bundle. Passing the gate met the specified comparison; it did not establish an acceptable operational false-approval rate.
Normal: The model manifest recorded the feature order, class names, library versions and artifact hashes. The service validated the bundle at startup and mapped probabilities using the model's class labels. The saved model, scaler and supporting code are required together. The model stayed static during operation, so completed verifications did not trigger online learning, and legacy artifacts were kept separately to allow comparison and rollback.

Heading 3: 5.4.4 Error Analysis and Interpretation
Normal: Class imbalance and overlapping scenarios explain why accuracy alone overstated useful review performance. Verified cases made up 60% of the fresh sample and had high recall, whereas Manual Review cases frequently resembled Verified cases in the observed feature space. The simulator deliberately included indistinguishable components with different latent labels, and the stored identifiability analysis attributed a minimum eight-percentage-point population error contribution to them, with further overlap adding more. This is a property of the simulation and not an estimated limit for real identity verification.

Normal: For classification, version 3 achieved 75.800% accuracy and 0.654082 macro F1 on the fresh synthetic sample and passed its comparative release gate. The improvement over version 2 was inconclusive. Liveness and face matching carried most of the measured importance, which is consistent with the emphasis in the literature on liveness detection (Tan et al., 2014) and discriminative face embeddings (Deng et al., 2019) and supports the pipeline design in Chapter 3. The successful isolated passkey and retention tests supplied narrower evidence for those modules; no general security or privacy-compliance conclusion was drawn.
Heading 3: 5.7.3 Limitations
Normal: Data validity was the main limitation. The labels were synthetic, the class quotas were fixed and the score relationships were assumed. The fresh evaluation sample came from the same simulator and not from independent real applicants, and the benchmark measurements were reused from earlier runs, so later changes to the image pipeline could cause a mismatch between the source distributions and deployed scores.
Normal: Evaluation coverage remained limited. The live evidence comprised 12 requests from eight agent identifiers, with no independent identity labels or recorded model versions; it could not establish real-world accuracy. No demographic fairness study, presentation-attack campaign, camera comparison, participant usability study or timed ten-run pipeline benchmark was documented. Small calibration and selection partitions also left a risk of policy overfitting. Model metrics excluded the full effects of capture quality gates, fallback and administrator intervention. Completed hosting resolved the earlier deployment limitation, but did not provide measured cloud latency, concurrency or long-duration availability.
Normal: Retention and informed collection remain incomplete against the amended design. The verified-only cleanup and its passing local tests do not demonstrate the 30-day non-verified image policy, 180-day metadata expiry, abandoned-upload handling or preservation exceptions. The required consent control, backend record/enforcement and withdrawal route were not found. DR-08 and DR-09 therefore remain unresolved.
